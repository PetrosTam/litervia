## 2. D-04 — identity and source integrity

### 2.1 Key choice and controlled schemes

**Approved direction:** random internal IDs independent of upstream identifiers. **Proposed physical default (approved direction, not tested DDL):** PostgreSQL native `uuid DEFAULT gen_random_uuid` (UUIDv4) for identity tables; no extra extension. Stable work and appearance IDs must survive identical reruns, changes of assertions and supervised work redirects; never derive IDs from title, DOI, year, author name or source key. Every research source observation has a separate immutable `source_records.id` and unique (`snapshot_id`, `source_record_key`).

Preserve immutable snapshot hashes, selector/extractor contract version and source record raw exported values. `jsonb` reflects the exporter representation, **not proof of byte-perfect original XML**. Archived original XML and source datasets stay outside Git and the application database.

Identifiers are **claims**, not automatically verified identities. `dblp_key` is primarily the source-scoped `source_record_key` and must not be duplicated in `external_identifiers` by default. Explicitly permitted candidate scheme/owner pairs: `doi` → source observation, reviewed appearance or reviewed volume; `orcid` → person (only after separate identity review); other schemes and `ror`/institution owners are **DEFERRED**. No global `UNIQUE(doi)`; preserve every raw DOI and `<ee>` candidate, its provenance, syntax status and resolver status separately. Wrong owner/scheme pairs require database-level rejection when implemented.

### 2.2 Typed mapping (candidate SQL-level invariant)

A `source_record` has kind `inproceedings` or `proceedings`. The physical proposal uses all of the following in combination:

```sql
-- DESIGN PSEUDOSQL; NOT EXECUTED OR APPROVED AS A MIGRATION.
UNIQUE (source_records.id, source_records.record_kind)
FOREIGN KEY (source_record_id, source_record_kind)
 REFERENCES research.source_records (id, record_kind)
CHECK (num_nonnulls(appearance_id, volume_id) = 1)
CHECK (
 (source_record_kind = 'inproceedings' AND appearance_id IS NOT NULL)
 OR
 (source_record_kind = 'proceedings' AND volume_id IS NOT NULL)
)
```

The binding relation also has typed FKs to `work_appearances(id)` and `proceedings_volumes(id)`. Since `num_nonnulls(...)=1` excludes both-neither and both-present, and the composite FK matches the recorded kind, it cannot legitimately map a proceedings volume to a paper appearance. The actual migration must prove this with direct SQL negative tests; Laravel validation alone is insufficient. A CHECK cannot inspect a referenced table without an FK, so the composite kind FK is essential.

**Binding lifecycle choice (proposed refinement):** retain append-only `source_record_bindings` decisions and store the current mapping in a restricted `current_source_bindings` relation keyed by `source_record_id`; use a composite FK (`binding_id`, `source_record_id`) to bind the current pointer to a historical decision for **the same observation**. All pointer transitions require a transaction, an auditable decision with the correct binding (approved human review or a separately authorized deterministic rule), audit and server-side authority. This avoids claiming an updated `binding_state` history row is immutable. Zero current pointer is valid for unresolved/quarantined observations. The precise privilege/procedure to enforce transition audit is **OPEN D-12**, not assumed safe.

### 2.3 Byline and membership correctness

- `appearance_byline_sets` identifies a *particular appearance/source-observation* byline revision. Include `byline_observation_state` = `observed_authors | observed_empty | not_checked` (candidate values). `observed_empty` yields **zero `appearance_authorships` rows**, not a fictitious “anonymous” author.
- `appearance_authorships` primary key (`byline_set_id`, `position`), `position > 0`; preserve exact original names/attributes, including source-specific ordering and unresolved author identity. Different snapshots can disagree without overwriting history.
- **Required concrete lineage key:** `source_record_bindings` defines `UNIQUE (id, source_record_id, appearance_id)` (in addition to its ordinary PK). For an appearance byline set, all `source_binding_id`, `source_record_id`, and `appearance_id` are NOT NULL and carry `FOREIGN KEY (source_binding_id, source_record_id, appearance_id) REFERENCES research.source_record_bindings (id, source_record_id, appearance_id)`. This matches one immutable `inproceedings` binding, not three unrelated IDs. PostgreSQL `MATCH SIMPLE` permits nullable composite components to skip checks, so every referencing component is NOT NULL. Do not assume a plain FK to each column is sufficient.
- Do **not** retain `work_appearances.verified_volume_id`. Derive current verified membership from independently reviewed `appearance_volume_memberships`; preserve disputed and unverified candidates, with at most one current *confirmed* membership unless a future explicitly approved model allows multiple.
- Historical release display and work associations are pinned at release time; mutable present-day `work_appearances.work_id` must not be used to recalculate an older released result.
- Proceeding volumes never appear as research papers or inflate canonical work counts; no unsupported CHI 1984 edition is fabricated.

### 2.4 Exact decision-to-subject integrity (R-01 / R-02 — PROPOSED)

**R-01 / membership decisions:** A confirmed `appearance_volume_memberships` row must reference a decision for **that exact appearance-volume pair**, not merely a decision about either subject. The candidate `classification_decisions.decision_scope` distinguishes `membership` (both `appearance_id` and `volume_id` NOT NULL) from non-membership classification (exactly one typed subject). Require a candidate non-partial `UNIQUE (id, appearance_id, volume_id)` on the decision parent and composite FK `(classification_decision_id, appearance_id, volume_id)` from membership to the same parent columns. A confirmed membership requires all three referencing fields NOT NULL; otherwise PostgreSQL `MATCH SIMPLE` could bypass the FK. Its decision must additionally be `approved`, scoped to membership, backed by suitable evidence, and authorized for this transition; these **cross-row state/authority rules are not established by the FK** and need a restricted database-enforced confirmation boundary and negative SQL tests. Do not convert disputed membership into verified main CHI merely because an evidence row exists.

**R-02 / active source-binding decisions:** The `identity_decisions` source-binding variant records `source_record_id`, `binding_id`, `decision_kind = source_binding`, decision state, actor/basis, and supporting evidence or an accepted deterministic rule identifier/input hash. A composite FK on those two IDs points to the immutable binding row; candidate `UNIQUE (id, source_record_id, binding_id)` supports a second composite FK from `current_source_bindings (selected_decision_id, source_record_id, binding_id)` to **the matching decision**. All three current-pointer FK fields are NOT NULL. Historical binding rows do **not** hold a reverse `identity_decision_id` FK, avoiding a circular decision-to-binding dependency. A reviewed assignment requires the appropriate explicit reviewer approval; a permitted initial deterministic mapping requires a separately approved rule contract and auditable rule evidence, **not a fabricated human approval**. An FK alone cannot prove decision state, authorization or absence of a conflicting transition: enforce them in a restricted transactional boundary. Rejected, superseded or unrelated decisions cannot select the pointer.

### 2.5 Exact public byline reproduction (R-03 — PROPOSED)

**P2 / selected-byline mapping authorization (PROPOSED):** Matching composite FKs establish source-binding lineage, not permission to publish it. Before validating a release, the guarded validator must verify that the selected `appearance_byline_sets.source_binding_id` identifies the *same* source observation and appearance as the selected release item and has an eligible, evidence-backed `identity_decisions` approval (or a separately approved, auditable deterministic-rule decision) *at release-validation time*. A historical FK alone and the present-day `current_source_bindings` pointer are not proof of historical authorization. Pin the eligible decision and source binding in the immutable release manifest; reject unrelated, rejected, previously superseded or unauthorized decisions and fabricated rule authority. Later identity supersession must not silently rewrite a frozen release; effective rights withdrawal still overrides unsafe reads or rollback. The actual database guard and negative fixtures remain D-12 OPEN / NOT RUN.

Each `catalogue_release_bylines` row must carry non-null `source_byline_set_id` and `position` referencing the actual `appearance_authorships (byline_set_id, position)`, plus a composite FK `(release_id, appearance_id, source_byline_set_id)` into `catalogue_release_items (release_id, appearance_id, selected_byline_set_id)` with the necessary non-partial parent UNIQUE. This rules out mixing byline sets between releases/appearances. The controlled release validator additionally compares **the complete ordered set**, row count and each `public_name` to the selected original byline; for the current candidate contract, display-name transformations are **not permitted** without a separately designed, provenance-backed approval path. `observed_empty` means zero public byline rows and an explicit empty-source state; `not_checked` is not synonymous with observed empty and must not generate author names. A valid FK does not prove these cross-row count/value rules. Validate before freeze, deny direct writes after validation, and add wrong-name/wrong-position/cross-set/empty-bypass negative fixtures.

### 2.6 Exact published membership and classification selections (R-05 / R-06 — PROPOSED)

**R-05 / release-selected membership:** `publication.catalogue_release_items` may select a proceedings `volume_id` only together with a non-null `selected_membership_id`. A candidate same-row CHECK must require `(volume_id IS NULL AND selected_membership_id IS NULL) OR (volume_id IS NOT NULL AND selected_membership_id IS NOT NULL)`; this avoids nullable composite FK bypass for a present volume. Require the membership parent to have non-partial `UNIQUE (id, appearance_id, volume_id)` and a composite FK `(selected_membership_id, appearance_id, volume_id)` to the **exact** `research.appearance_volume_memberships` row. Keep the separate release-scoped FK `(release_id, volume_id)` to the published volume item. Both FKs are necessary but insufficient: the guarded release validator must additionally establish that the selected membership and its exact-pair decision were approved, evidence-backed and eligible at the time of validation. Freeze that selected membership and decision in the immutable release manifest; subsequent supersession must not rewrite a historical release. An unrelated published volume or membership for a different appearance is never acceptable.

**R-06 / published classification provenance:** `source_category` and `contribution_type` are **different claims**, and any public non-unknown or `verified main CHI` assertion needs an inspectable, subject-compatible approved classification decision (or an explicitly approved, evidenced deterministic rule), pinned to the release. Candidate nullable `selected_category_decision_id` and `selected_contribution_decision_id` reference the appropriate typed `classification_decisions` subject (appearance or selected volume as applicable). The validator must check scope, subject, authority/effective approval, underlying evidence and **exact equality of the published value** to the selected decision/rule result; record the selection and rule identity in the immutable release manifest. If evidence is insufficient, publish an honest `unknown` state rather than manufacturing approval. A DBLP `booktitle` heuristic, source volume presence or a membership decision alone does not justify verified-main classification. The release's `catalogue_release_volume_items.source_category` follows the same subject-backed decision/rule requirement, not merely the appearance-level category. The final typed FK shapes and deterministic-rule authority remain D-12 OPEN, not implicitly implemented by nullable decision IDs.

### 2.7 Decision authority and audit identity (R-08 — PROPOSED)

**P2 / deterministic-rule execution provenance (PROPOSED):** The candidate `identity_decisions` and `classification_decisions` dictionaries each add `rule_execution_ref text?`, pointing to immutable, versioned execution evidence containing the approved rule identifier/version, actual executing service identity, input hash, selected result and execution timestamp. For `decision_basis = approved_deterministic_rule`, this reference and its evidence must be required and independently validated; for human decisions, preserve a genuine authorized reviewer record rather than fabricating rule execution or reviewer identity. A text reference alone is not a foreign-key/authorization proof: the final durable evidence relation, enforcement mechanism, and its privileges remain D-12 OPEN.

A `classification_decisions` record must distinguish `human_review` from `approved_deterministic_rule` through an explicit `decision_basis`, with an immutable actor/reviewer audit reference for a human approval, or an approved rule reference plus input hash and execution identity for rule-driven selection. Both retain the decision state, rationale, source/evidence link and recorded time. A non-null reviewer reference is not itself proof of authorization: the controlled decision/confirmation boundary must verify permission, approval validity, supersession and audit linkage. Do not assign a fabricated human reviewer to deterministic mappings. Exact reviewer account/role policy and database-enforced audit guard remain D-12 OPEN; test unauthorized, rejected, revoked and wrong-subject approvals before use.

**Enforceability clarification (REV-01/02/03/04; R-01/02/03):** A typed CHECK proves only same-row conditions. Cross-row evidence status, byline cardinality, source-to-canonical claim lineage, approval state, and effective rights must be validated by a reviewed transaction/trigger/controlled function or a more precise relation shape before they can be claimed database-enforced. Candidate FKs may require additional supporting parent UNIQUE constraints. A missingness state is not a substitute for original evidence. A confirmation cannot rely on nullable decision/evidence IDs.

**Table-list status:** These are *candidate relations*, not a frozen count or an instruction to create all tables. The `publication_holds` mechanism and publisher-specific identity, reviewer authority, source assertion subject types and several relationships need separate sign-off. Defer institutions, historical affiliations, awards, abstracts, media and enhancement adapters unless verified source facts and rights justify them.

## 4. D-05 — immutable publication and recovery contract

**Approved direction:** staged source import → validation → immutable release snapshot → explicit publication authority → catalogue-local atomic pointer → audited rollback; never infer a distributed transaction with `litervia_private`.

**Proposed candidate transaction:** (1) verify a validated, immutable release/manifest; (2) verify approved completeness and rights gates; (3) BEGIN and lock singleton `active_release` row; (4) recheck expected generation and active rights holds; (5) update `active_release.release_id` and increment generation; (6) insert the matching `release_transition_events` event in **the same transaction**; (7) COMMIT. A failure before COMMIT leaves the old pointer and no committed promotion event. A trigger/controlled function or equivalent DB-enforced boundary must prevent bypass and unaudited direct UPDATE; **not currently implemented**.

**Snapshot immutability:** Freeze membership for appearances **and volumes**, selected title/DOI/source links, observed/missingness states, ordered public byline, reviewed category/type, exact work association and source/evidence selection. A release A→B→A must return the same authorized *historical facts*. A current correction cannot mutate A. Every selected title assertion/byline FK must be checked for *the same appearance*, not merely point to an existing row. Do not accidentally follow the latest mutable identities when reading historical snapshots.

**Publication validator (REV-02/03):** Before a release is marked validated, require every public title to match a selected, existing, evidence-backed field assertion belonging to the correct appearance/volume (the DBLP fallback must be a separately mapped derivative of a preserved source-only assertion); ensure non-null byline-set selection is appearance-compatible (including an explicitly observed-empty set); ensure volume selection is release-scoped and its membership review is approved; verify work-identity basis, attributed DOI/source links and rights state. The freeze boundary must reject subsequent INSERT/UPDATE/DELETE against validated release contents, not merely revoke DML from the public app. An FK from `active_release.release_id` to `catalogue_releases.id` proves only row existence; it **cannot** prove `validated_at IS NOT NULL`, approval, completeness, effective rights or immutability. Those are controlled publication-transaction guards requiring real negative tests. Until a reviewed guard is implemented, the design is **NOT SAFE FOR PUBLICATION**.

**Request consistency:** A catalogue HTTP request involving multiple SQL queries (results, facets, counts) must pin one active release ID or use a safe transaction snapshot; a concurrent promotion cannot mix A and B within one response. Pagination cursor/sort/API details remain D-10 OPEN.

**Rights withdrawal precedence (P0; R-07 clarification):** Immutable history is not a licence to continue serving withdrawn material. The public read path **must enforce effective publication holds on every authorized response**, **and** guarded promotion/rollback must reject any target release containing disallowed material. Both protections are required, not alternatives. The final hold scope, database-enforced guard and concurrent rights-withdrawal coordination remain OPEN; a race must fail closed rather than expose revoked content. Never let direct historical-release queries or cached views bypass a hold. Explicitly test active reads, A→B→A rollback, concurrent withdrawal and authorization boundaries. **No public launch while this mechanism remains unresolved.**

**Release approval gates OPEN:** who can validate/promote; source/sample coverage threshold; how to handle partial reviewed rejections; reviewer attestations and independent audit; emergency takedown authority; retention/correction window. **No source completeness or rights status is fabricated.**

## 5. D-12 — roles, privileges and dependent migration order (OPEN)

### 5.1 Existing and proposed roles

| Principal | Existing? | Permitted *target* access | Prohibited access |
|---|---|---|---|
| `litervia_catalogue_app` | **VERIFIED EXISTING** | `USAGE` on `api_public` + `SELECT` on reviewed public projection views *only* | `research` / `publication` base SELECT, any DML, DDL, staging, reviewer data, migration credentials, other DB CONNECT |
| `litervia_catalogue_migrator` | **VERIFIED EXISTING** | Separately approved DDL operations, migration windows only | Ordinary web requests; uncontrolled release promotion; other DB CONNECT |
| `litervia_catalogue_importer` | **PROPOSED NOT CREATED** | Narrow staging/source upsert and ingest audit in catalogue only | Publication pointer, unreviewed evidence exfiltration, DDL, private DB |
| `litervia_catalogue_publisher` | **PROPOSED NOT CREATED** | Guarded promotion and rights-action functions after sign-off | General arbitrary DML on source/provenance, DDL, private DB |
| `litervia_private_app` | **VERIFIED EXISTING** | Its own private DB subject to Laravel ownership policies | Catalogue DB connection or access |

Proposed schemas `research`, `publication` and `api_public` require explicit schema grants; the existing foundation uses `public` schema privileges. No role, table, schema or new grant is provisioned by this design.

**R-04 / Laravel connection integration (PROPOSED):** The existing `config/database.php` catalogue connection uses `search_path = public`, while future read views belong to `api_public`. Prefer explicit, schema-qualified names such as `api_public.<allowlisted_view>` in future Laravel catalogue reads; do **not** add `research` or `publication` to the web connection's search path, expose base tables, or change any runtime config in this documentation PR. If a `search_path` change is later preferred, require its own approval and authenticated connection/config-cache/security tests. In either approach test that legitimate public views resolve while unqualified/base-table reads, shadow objects and forbidden grants cannot bypass the read-only projection.

**Public projection trust model (REV-05):** Owned by a dedicated NOLOGIN owner/migration-controlled principal, not the web login; explicit SELECT-only projections, never `SELECT *`. Use ordinary owner-privileged views only after confirming the view owner can access needed base rows and `litervia_catalogue_app` cannot access research/publication base relations directly. Do not set `security_invoker=true` blindly: it may require base-relation access for the web principal. Evaluate `security_barrier=true` **when untrusted caller predicates or optimizer reordering could expose protected rows**; it is not a substitute for verified view ownership, rights predicates, function security, or least privilege. A public view must never expose stage, reviewer notes, unrestricted historical releases, or a route bypassing an effective rights hold. Threat cases include crafted WHERE predicates/functions, views over historical releases, sensitive text in errors/logs, concurrent rights withdrawal, and untrusted `search_path`/SECURITY DEFINER functions. Restrict function/procedure EXECUTE (including PostgreSQL default PUBLIC function EXECUTE), table/sequence/schema privileges, object ownership and future-object `ALTER DEFAULT PRIVILEGES`; no runtime DDL or base-table DML. Use actual PostgreSQL 18 authenticated roles for positive and negative probes; **all such probes remain NOT RUN**.

**P1 / row-filtering public-view security gate (PROPOSED):** Any `api_public` view whose predicates enforce visibility of individual records, active-release membership or effective publication-rights holds must use `security_barrier=true` before it is accepted as that row-security boundary. Test malicious/leak-prone caller predicates and operators with actual restricted PostgreSQL 18 fixtures, confirm the view owner and function permissions, and test that historical release queries cannot bypass the rights filter. A projection-only view need not have a security barrier *solely for column selection* when every underlying row is independently safe to expose; document and test that distinction. `security_barrier` is not a substitute for release consistency, row eligibility, rights-withdrawal synchronization, least-privilege grants, function EXECUTE lockdown or cache controls; evaluate its planner/performance costs. No such view or tests are currently implemented.

### 5.2 Dependency-ordered migration design (NO execution approval)

1. Schema creation, role/owner trust mapping and grants plan; **do not rerun non-idempotent foundation provisioning**.
2. Source snapshots, source evidence, source records and canonical work/appearance/volume scaffolding, with simple non-circular FKs.
3. Typed source-record binding history first, then source assertions, identifiers, byline sets, authorships and binding-scoped identity decisions; only after decision parent UNIQUE/FKs, create current pointers. Avoid reverse decision FKs and unreviewed circular dependencies.
4. Classification decisions with explicit subject-pair scope first, then appearance-volume memberships using the exact-pair composite FK, followed by redirects; no unreviewed identity collapse or speculative authors/institutions/media.
5. Ingestion run audit and deterministic fixture reconciliation; all staging remains invisible to public app.
6. Immutable release content and selected-assertion/byline composite integrity; publication holds/withdrawal policy *only after approval*.
7. Controlled pointer/event transaction; view owner/ACL/default-privilege lockdown; repeat privilege probes using actual roles and PostgreSQL 18.
8. Only in future independently authorized stages: zero/positive/negative test fixtures, then approved 150-source-observation pilot and publication readiness assessment.

**Risk points:** Circular `membership → classification decision → appearance/volume` dependencies require creating decision targets before membership references or staged `ALTER TABLE` with valid FKs; do not use unchecked constraint disabling. If byline sets require a binding composite, define the parent UNIQUE first. A release FK to (`release_id`, `volume_id`) must match an actual released volume item; a source assertion selection must match its appearance. Work redirect cycles and permission/effective-withdrawal checks cannot be solved by a single same-row CHECK.
